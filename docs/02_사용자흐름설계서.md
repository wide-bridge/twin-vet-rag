# TwinVet Care 사용자흐름 설계서

버전: 0.8 · 작성일: 2026-11-09 · 상태: 개발 검토용 초안 (0.6, 2026-11-13: MVP1 HITL 데이터 파이프라인 흐름 / 0.7(2026-11-14): 수의사 없이 진행하는 출처 근거 갈래·로컬 비교·되돌리기 기준 / 0.8(2026-11-14): HITL 검토 도구 운영 배포 완료(hitl-review.pawcheck.ai), vet.pawcheck.ai는 M03 병원 화면용, M03을 다음 개발 단계로 결정)

세부 흐름은 서비스 기획서의 확정 사항과 PM 기본안에 따른다.

## 1. PoC 보호자 흐름

```text
시작 화면(S01): 서비스 범위·데이터 처리 안내
 → 상담 시작(P01)
 → 상담 화면(S02): 반려견 정보 입력(이름 선택, 품종·나이 필수, 건강상태 선택) → 질문 입력
 → 질문 검증 → 검색 → 답변 생성(P02)
 → 답변과 출처 확인(P03)
 → 후속 질문(P04) 또는 피드백(P05)
 → 새 상담 시작 / 현재 대화 삭제
```

| 상황 | 서비스 동작 | 사용자 다음 행동 |
|---|---|---|
| 정상 질문 | 질문을 저장하고 답변 준비 상태 표시 | 답변과 근거 확인 |
| 후속 질문 | 현재 상담의 맥락을 참조해 검색 | 추가 질문 또는 종료 |
| 정보 부족 | 필요한 정보를 짧게 질문 | 보충 입력 |
| 근거 부족 | 근거 부족 상태를 명시. 근거 있는 답변처럼 표현하지 않음 | 질문 구체화 또는 전문가 상담 |
| 지원 범위 밖 | 지원 대상(반려견)과 주제를 안내. 고양이 등 다른 동물 질문 포함 | 지원 범위의 질문 입력 |
| 반려견 정보 누락·형식 오류 | 품종·나이 누락 또는 허용 범위 밖 값은 전송 전 해당 항목에 오류 표시. 서버도 422로 거부 | 값 수정 후 전송 |
| 질문과 입력 정보 불일치 | 예: 입력 나이와 질문 속 나이가 다름(생애주기가 다르고 2년 넘게 차이). 생년월(일)로 입력했으면 확인 질문(clarification), 출생 연도만·추정 나이면 질문 속 나이를 따라 답변 | 확인 답변 또는 새 상담에서 정보 수정 |
| 모델·검색 장애 | 실패 상태 표시. 성공 답변으로 저장하지 않음 | 같은 요청 재시도 |
| 중복 전송 | 같은 요청 ID에 대해 한 번만 처리 | 기존 처리 결과 확인 |
| 처리 중 새로고침 | 요청 상태를 조회해 처리 중·완료·실패 복구 | 완료 대기 또는 재시도 |
| 세션 만료 | 이전 대화 접근 제한과 새 상담 안내 | 새 상담 시작 |
| 대화 삭제 | 확인 후 세션의 상담 데이터 삭제 처리 | 새 상담 시작 |

반려견 정보는 첫 질문 전에 입력한다. 품종(모름·믹스견 허용)과 나이는 필수다. 나이는 생년월일을 아는 데까지(년 필수, 월·일 선택) 입력하고, 모르면 '정확히 몰라요'를 골라 추정 나이(년·개월)를 입력한다. 생일(일)은 향후 생일 이벤트를 위해 받지만 화면에는 생년월일을 표시하지 않고 나이만 표시한다(나이와 중복되므로, 2026-11-11 사용자 결정). 이름은 선택이며 요약 표시와 답변에서 반려견을 부르는 데만 쓴다. 건강상태는 선택이며, 건강상태(체중, 중성화 여부, 기존 질환·복용 약)는 건너뛸 수 있다. 첫 질문을 보낼 때 입력값으로 상담을 생성한다. 같은 상담에서는 정보를 유지하고 변경은 새 상담에서 한다. 서버는 나이로 생애주기(자견·성견·노령견)를 산출해 검색에 쓰고, 산출값과 공통·미지정 자료를 함께 검색한다. 입력 정보는 상담 화면 상단에 요약 표시해 보호자가 어떤 정보로 답변받는지 알 수 있게 한다.

처리 중에는 같은 상담의 다음 전송을 막는다. 답변이 나오면 입력을 다시 활성화한다. 익명 세션은 같은 브라우저의 유효한 세션에서만 유지하며 기기 간 동기화를 보장하지 않는다.

### 1-1. 설정·주치동물병원·케어 — P08·P09 (2026-11-12)

```text
첫 방문: S02에서 반려견 정보 입력 → 첫 질문 전송 → 프로필 저장(P08) → 상담 진행
 → 첫 상담 후 안내: "주치동물병원을 등록해 두면 응급 시 바로 전화할 수 있어요" [등록] [나중에]
재방문: S02 상단 요약 "두부(푸들) | 11세 5개월 | 5kg [변경]" 확인 → 바로 질문
 → [변경] 또는 설정 탭(S09): 반려견 정보·주치동물병원 수정 → 다음 상담부터 적용
응급 안내 누름: 주치동물병원 전화 / 24시 동물병원 찾기 / 전화할 때 말할 것
케어 탭(S08): 상담 카드 목록 → 다시 열기 / 삭제 / 병원에 보여주기
```

| 상황 | 서비스 동작 | 사용자 다음 행동 |
|---|---|---|
| 프로필 없음(첫 방문·브라우저 데이터 삭제) | 지금처럼 S02에서 반려견 정보 입력. 첫 질문 때 프로필도 저장 | 입력 후 질문 |
| 프로필 변경 | 다음 상담부터 적용. 진행 중·지난 상담의 반려견 정보는 그 시점 값을 유지 | 새 상담에서 확인 |
| 주치동물병원 미등록 + 응급 안내 누름 | 24시 동물병원 찾기를 먼저 보여 주고, 등록은 아래에 작게 안내. 입력을 요구하지 않음 | 전화 또는 지도 검색 |
| 주치동물병원 등록 + 응급 안내 누름 | 병원 이름과 전화 버튼(모바일은 바로 전화, PC는 번호 표시) + 24시 동물병원 찾기 | 전화 |
| 같은 날 같은 주제로 여러 번 상담 | 케어에서 하나의 묶음 카드로 표시(건별 카드는 펼쳐서 확인). 새 상담 시작 시 오늘 상담 이어서 묻기 제안 | 이어서 묻기 또는 새 상담 |
| 상담 만료(7일) | 케어 목록에서도 사라짐. 프로필·주치동물병원은 유지 | — |

주치동물병원 찾기: [병원 이름·동네 검색] 또는 [내 주변](위치 권한, 위치는 저장하지 않음) → 카카오 검색 결과 목록(실시간) → 병원 선택 → 서버가 공공데이터와 매칭 → 전화번호 확인·입력 → 저장. 매칭 실패면 이름 직접 입력 + 카카오 장소 링크 저장, 검색 장애면 직접 입력.

프로필은 계정 없이 브라우저별 익명 프로필 키로 찾는다. 다른 기기에서는 보이지 않으며 기기 간 동기화는 MVP 계정 기능에서 다룬다.

## 2. PoC 운영자 흐름 — P06

```text
원천·사용 조건 확인
 → Training/Validation 분리·중복 검사
 → qa_case/reference 구분·줄바꿈 정규화·출처 부여
 → 문서 버전 저장 → 유형별 청크 → 비용 표본 측정·예산 확인 → 임베딩·색인
 → 표본 검색 검증 → 새 버전 활성화
```

- 적재 실패: 기존 활성 버전을 유지하고 실패 원인을 기록한다.
- 수정: 새 버전을 검증한 뒤 활성 버전을 전환한다.
- 삭제·비활성화: 검색에서 즉시 제외하고 관련 청크·벡터 삭제 작업을 확인한다.
- PoC에서는 Validation 2,400건을 평가 전용으로 분리하고 검색 색인에 넣지 않았다. MVP1부터는 지식 구축·라벨링에 활용한다(서비스 기획서 7절 혼합안). 153번은 사용하지 않는다.
- 출처 화면은 이용 조건 확인 전 문서명·출처만 제공한다. 원문 발췌는 서버에서도 반환하지 않는다.
- 기존 답변의 출처가 삭제되면 상세 구절을 노출하지 않고 ‘현재 제공 불가’로 표시한다.

## 3. MVP1 온톨로지 활용 — M01

MVP1에서 온톨로지 0.1은 먼저 **라벨링의 공통 의미 기준**으로 쓴다(수의사가 증상·부위·권고를 같은 코드로 기록). 검색·답변 결합은 수의사 확정 후 단계적으로 적용한다.

```text
질문 → 문서 검색 + 구조화 지식 조회
 → 근거·관계·조건 확인 → 답변 생성 → 근거 표시
```

조회 결과가 없거나 문서 근거와 충돌하면 상태를 기록하고 불확실성을 표시한다. 충돌한 내용을 확정 사실로 합치지 않는다. 개념·관계는 초안(draft)과 확정(approved)을 구분하며 수의사 확정 전 개념은 답변 근거로 쓰지 않는다.

## 4. MVP1 수의사 HITL 데이터 파이프라인 — M02 (2026-11-13 확정)

```text
① 평가: 검토 묶음 생성 → (AI 라벨 초안) → 수의사 라벨링 → 자동 점검 → 제출
② 재검증: 다른 수의사의 독립 라벨링(제출 전 서로의 라벨 숨김) → 일치 / 이견(유형 기록) → 조정
③ 지식 발행: 재사용 범위 심사 → 비식별화·적용 조건 명시·중복·충돌 검토
   → 지식 후보 버전 → 발행 승인(내용 해시에 연결, 작성·수정자 아닌 수의사) → 검색 영향 점검 → 활성화
```

- **검토 묶음**: 질문 + 이전 대화 + 당시 반려견 정보 + AI 답변 + 실제 인용 근거 + 모델·프롬프트·지식 버전. 오류가 검색에서 났는지 답변 생성에서 났는지 구분하기 위함이다. 묶음은 생성 시점의 복사본으로 고정한다.
- **묶음의 출처**: 데이터셋 질문(AI Hub)으로 생성한 답변, 모의 데이터, (동의를 받은 경우) 실제 상담. 실제 상담 사용 조건은 보관·동의 정책 확정 후 연다.
- **검토 상태**: draft → vet_reviewed → independently_verified, 또는 disputed. 이견 유형: 정보 부족 / 근거 충돌 / 허용 가능한 견해 차이. 다수결로 확정하지 않는다.
- **재검증 대상**: 초기에는 같은 표본을 두 수의사가 독립 라벨링해 기준을 맞춘다. 이후 판단 불가·이견, 안전 관련 수정, 지식 발행 후보는 반드시 독립 재검토하고 일반 사례는 표본으로 재검토한다. 같은 수의사의 자기 점검은 독립 검증을 대신하지 않는다.
- **발행 상태**: unapproved → approved → active. 승인 후 내용이 바뀌면 다시 승인한다. 검색 영향 점검이 실패하거나 '평가 불가'(질문·비교 색인 부족)면 활성화하지 않는다. 적용 조건은 발행 본문에 함께 넣어 답변 모델이 보게 한다. 사례는 사례로, 일반 지식은 별도 근거와 검토를 거쳐 따로 발행한다.
- **모의 데이터**: 시험 환경에서는 활성화까지 검증하지만 운영 검색에는 절대 들어가지 않는다(코드로 차단).
- 수의사 0명인 A단계에서는 운영자가 화면·흐름을 시험한다. 운영자·AI 라벨은 검토 완료로 세지 않는다.

### 4-1. 수의사 없는 흐름 — AI 답변 품질 점검 (2026-11-14 확정)

```text
묶음 생성: 실제 질문(색인에 없는 Validation 질문) → 앱과 같은 RAG 답변 → 사용한 근거 저장
자동 점검(AI): 검색 적합성, 주장별 근거 대조, 출처 연결 오류, 적용 조건 누락, 금지 내용, 원천 답변과의 일치(참고)
운영자 확인: 질문·답변·근거를 비교해 오류 유형 기록. 의학적 판단이 필요한 건은 보류
개선: 검색 실패·출처 연결 오류·조건 누락·근거 없는 조언·원천 반복 문구 등 확인 가능한 문제만 수정
재점검: 같은 사례로 다시 답변·점검해 전후 비교 → 효과가 확인된 변경만 운영 반영(되돌리기 가능)
```

- 자동 점검 결과는 검토 상태를 바꾸지 않는다. 화면에는 '자동 점검 결과(안전성·수의학적 검증 아님)'로 표시한다.
- **비교 단위**: 한 번에 한 가지만 바꾼다. 현재 데이터+현재 프롬프트(기준) → 현재 데이터+수정 프롬프트 → 정제 데이터+수정 프롬프트.
- **비교 입력 고정**: 같은 사례는 질문·반려견 정보(나이·생애주기 포함)·이전 대화·검색 설정을 첫 실행 값 그대로 다시 쓴다. 재실행 때 반려견 정보를 질문에서 다시 추정하지 않는다(나이가 없는 질문은 생애주기 필터가 달라질 수 있음).
- **사례 구분**: 개발용 5건(오류 수정 확인)과 확인용 10건(변경에 쓰지 않은 사례). 확인용 사례를 보고 다시 수정하면 그 사례는 개발용으로 옮기고 사용 이력을 실행 기록에 남긴다. 15건은 명시한 ID 목록으로 eval_dev에서만 고르고, 실행 전에 각 사례가 대상 색인에 없는지 확인한다. eval_final은 마지막 확인에만 쓰며 일반 점검 명령(검색 영향 점검 질문 선택 포함)도 쓰지 않는다.
- **Validation 방침과 현재 상태 구분**: 방침은 Validation 전체를 지식 구축·라벨링에 활용하는 것(기획서 7절)이지만, 현재 색인은 Training만 담고 있다. 묶음은 아직 색인에 없는 Validation 질문으로 만들며, 이후 Validation을 색인에 넣으면 해당 사례는 비교에서 빼거나 자기 사례를 검색에서 제외한다.
- **운영자 검토 대상**: 응답 상태가 같아도 본문에서 조언이 빠지거나 더해질 수 있으므로 15건 모두 변경 전후 답변을 나란히 본다. 자동 점수가 크게 바뀐 사례는 점검기 편향 여부를 직접 확인한다.
- **답변 누락 판정**: 근거가 질문과 관련 있는지뿐 아니라 답을 뒷받침할 만큼 충분한지 본다. 충분한 근거가 있는데 답하지 못하면 회귀, 관련 자료가 있어도 답에 필요한 정보가 없어 '근거 부족'이 되면 정상 동작이다. 기록은 '검색 단계에서 제한됨 / 답변 단계에서 제한됨'으로만 나누고 원인은 응답을 보고 확인한다.
- **사용자 검토**: 반복 문구는 대표 표본 10~15건과 애매한 문구만 삭제 전후·제거 이유와 함께 제시한다. 애매한 문구는 이번 정제에서 제외한다.

## 5. 보호자·수의사 질문·답변 연결 — M03 (2026-11-14 기획 초안)

범위·완료 기준은 서비스기획서 4-1절. 이전 판의 '검토 요청 → 배정 → 승인/수정/추가 질문' 흐름은 이 절로 대체한다.

```text
[보호자 · twinvet]                         [수의사 · vet]                       [HITL · hitl-review]
설정 > 수의사 연결: 목록에서 선택 → 연결 요청 ─▶ 연결 요청 수락 / 거절
                                  ◀─ 연결됨(또는 거절됨)
AI 답변 아래 [수의사에게 질문 보내기]
 → 공유 내용 확인(질문·AI 답변·반려견 정보 항목 선택,
   품질 개선 활용 동의는 선택) → 보내기 ────────▶ 받은 질문 목록 → 상세 → 회신 작성·전송
 → 원래 질문에 '수의사 확인 대기'
                                  ◀─ 회신
 '답변 완료' + 수의사 답변 카드(AI 답변과 구분)
                                                    (동의 + 회신 완료 질문만) ── 운영자 명령 ─▶ 검토 묶음(origin=consultation)
```

- **연결 상태**: requested → accepted / declined. requested는 보호자가 취소하면 cancelled. accepted는 보호자·수의사 누구나 해제하면 ended. 같은 보호자·수의사 사이의 진행 중 연결(requested·accepted)은 하나만.
- **질문 상태**: sent → answered. sent는 보호자가 취소하면 cancelled. 연결이 해제되면 회신 전 질문은 cancelled(사유 link_ended). answered 이후에는 보호자가 삭제만 할 수 있다(양쪽 화면에서 사라짐).
- **공유 단위**: AI 답변 1건과 그 질문. 이전 대화는 보내지 않는다(필요한 맥락은 보호자가 질문 문장에 넣음). 반려견 정보는 보호자가 고른 항목만(기본: 품종·나이·체중·중성화 / 기본 꺼짐: 이름·건강 메모).
- **재접속**: 같은 브라우저는 반려견 프로필 쿠키로 자동 확인. 다른 기기·쿠키 삭제에 대비해 보낸 직후 질문별 확인 링크를 한 번 보여 준다(그 질문 하나만 열림).
- **회신 확인 알림 없음**: 보호자는 앱에 들어와 상태를 본다. 응답 시간을 약속하지 않으며, 응급은 기존 응급 안내(주치동물병원·24시 병원)로 보낸다.
- **수의사 비활성화**: 새 연결·질문 불가. 이미 받은 회신은 보호자에게 남는다.

### 참고: 상담 상단 반려견 요약 (P02)

상담 상단에는 '이름(품종) | 나이 | 체중'으로 요약한다(예: '두부(푸들) | 11세 5개월 | 5kg'). 이름이 없으면 품종만, 체중이 없으면 생략한다. 나이는 생년월을 알면 'N세 M개월', 출생 연도만 알면 '약 N세', 추정이면 '약 N세 M개월(추정)'로 정확도를 구분한다. 생애주기 명칭·나이 구간은 표시하지 않으며 생애주기 선택 흐름도 추가하지 않는다.
