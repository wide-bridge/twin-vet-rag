## 1. 목적과 역할

반려견 보호자가 상담 자료를 근거로 질문에 대한 정보를 얻고 후속 질문을 이어갈 수 있는 서비스를 만든다.

- PM: 범위·사용자흐름·데이터·기능·화면·완료 기준 정의.
- Claude Code: 개발자 관점의 문서 검토, 확정 스택에 따른 구현·테스트·배포. Codex는 PM으로 단계별 결과를 검토한다.
- 기존 TwinVet 기획 자료는 참고 자료다. 기존 기능·수치·일정을 이번 요구사항으로 자동 적용하지 않는다.
- GitHub: https://github.com/wide-bridge/twin-vet-rag — 확인 시점에는 README와 .gitignore만 존재한다.

## 2. 단계별 범위 — 사용자 확정

| 단계 | 범위 | 완료 결과 |
|---|---|---|
| PoC | 일반 RAG 기반 서비스. 디자인·DB·백엔드/API·프론트엔드·통합 테스트·배포 포함 | 실제 사용 흐름을 갖춘 배포 가능한 상담 서비스와 평가 결과 |
| MVP1 (2026-11-13 확정, 11-14 보완) | 수의사 HITL 데이터 파이프라인(평가 → 재검증 → 지식 발행)과 온톨로지 0.1. 수의사 없이 진행하는 출처 근거 갈래(AI 답변 품질 점검 → 원천 정제·재색인) | A단계(완료): 모의 흐름 PoC. 현재 MVP: 출처 근거 개선을 비교·반영하고 되돌릴 수 있는 것(4절). 수의사 갈래는 수의사 확보 후 |
| MVP2 | PawCheck 소변 검사 스티커 CNN 판독 | 별도 관리(이 문서 범위 밖) |
| 후속 | 보호자 대상 수의사 답변(M03), 스마트 포티(Poochnio) | M03은 다음 개발 단계로 결정(2026-11-14, 4-1절). 보호자 공개는 법률 검토·병원 확보 후. 스마트 포티는 미정 |

PoC는 단순 실험 스크립트에 그치지 않는다. PoC 구현의 재사용 여부는 개발 검토에서 판단한다. 이전 판의 'MVP = 지식그래프/온톨로지 + 수의사 HITL'은 위 MVP1로 대체한다. 온톨로지는 독립 단계가 아니라 HITL과 RAG가 함께 쓰는 의미 기준으로 MVP1에서 작게 시작한다.

## 3. PoC 기능 — PM 제안 기본안

반려견 고정, 반려견 정보 입력(품종·나이·건강상태), 데이터 구분, 개발 스택은 확정 기준이다. 익명 세션·이력·피드백 등 나머지 세부 기능은 기존 PM 기본안이며 개발 검토 대상이다.

| ID | 기능 | 범위 |
|---|---|---|
| P01 | 상담 시작 | 로그인 없이 익명 세션으로 시작. 반려견 고정. 처음에는 반려견 정보(이름 선택, 품종·나이 필수, 건강상태 선택)를 입력하고, 그 값은 설정(P08)에 저장된다. 이후 상담은 저장된 정보 요약을 확인하고 바로 질문 |
| P02 | RAG 상담 | 질문과 필요한 대화 맥락을 이용해 검색·답변 생성 |
| P03 | 근거 확인 | 답변에 연결된 문서명·출처 표시. 원문 발췌는 이용 조건 확인 전 비활성화 |
| P04 | 후속 질문·현재 대화 | 현재 세션에서 질문을 이어가고 대화 확인 |
| P05 | 피드백 | 답변별 도움 여부와 선택적 의견 수집 |
| P06 | 지식 데이터 관리 | 운영자가 명령 또는 스크립트로 적재·재색인·비활성화 |
| P07 | 예외·운영 | 근거 부족·범위 밖 질문·장애 안내, 로그·기본 모니터링 |
| P08 | 설정: 반려견 프로필·주치동물병원 | 반려견 정보와 주치동물병원을 Neon DB에 저장하고 상담 시작·응급 안내에 사용. 병원은 카카오 로컬 검색으로 찾고 공공데이터(행정안전부 동물병원) 기준으로 저장. 반려견 1마리 |
| P09 | 케어: 상담 기록 | 보관 중인 상담을 건별 카드(날짜·주제 아이콘·질문·AI 요약·상태)로 보여 주고, 다시 열기·삭제·병원에 보여주기 제공. 건강관리로 단계 확대 |

PoC 기본안에서 제외: 회원가입, 반려견 외 동물(고양이 등), 여러 마리 반려견 프로필, 여러 기기의 프로필·상담 동기화, 이미지·영상 상담, 병원 예약, 결제, 수의사 검토 화면, 지식그래프/온톨로지, 센서 연동. 필요하면 범위를 명시적으로 변경한다.

## 4. MVP1 — HITL 평가·재검증·지식 발행 파이프라인 (2026-11-13 확정)

현재 진행 단계: A단계(수의사 참여 기반 구축) 완료, **수의사 없이 진행하는 출처 근거 갈래** 진행 중(아래 '수의사 없이 진행하는 MVP1' 참고).

수의사의 참여는 목적이 다른 두 업무로 나눈다. 같은 수의사가 둘 다 할 수 있지만 하나의 업무로 묶지 않는다.

| 구분 | 가. 보호자에게 답하기 (M03, 후속) | 나. 지식 품질 관리 (M02, MVP1) |
|---|---|---|
| 목적 | 해당 보호자의 질문 해결 | 이후 AI 답변의 품질 개선 |
| 대상 | 현재 반려견의 상황과 질문 | 고정된 질문·AI 답변·검색 근거·맥락 |
| 결과물 | 답변·추가 질문·후속 안내 | 구조화된 평가, 수정안, 근거, 적용 조건 |
| 선행 조건 | 비대면 상담 법률 검토, 수의사 확보, 응답 시간 | 라벨링 도구·지침, 수의사 참여 |

| ID | 기능 | 범위 |
|---|---|---|
| M01 | 온톨로지 0.1 | 증상·부위·질환·검사·관찰·권고의 개념·관계·조건·출처·버전을 PostgreSQL 테이블로 관리. 라벨링에 필요한 개념만 먼저 정의. 그래프 DB는 쓰지 않음. 이후 검색 보강(동의어·품종·나이 조건), 위험 증상 규칙, 케어 기록 연결에 사용 |
| M02 | 수의사 HITL 데이터 파이프라인 | ① 평가(라벨링) → ② 재검증 → ③ 지식 발행. 상담 답변이 검토 없이 공용 지식이 되지 않게 단계별 책임을 나눔 |
| M03 | 보호자·수의사 질문·답변 연결 (MVP1 밖, 다음 개발 단계) | 보호자가 수의사를 선택·연결하고 고른 질문만 보내 회신을 받는다. 수의사 없이 시험 계정으로 개발·검증하고, 실서비스 개방(실제 수의사·법률 검토) 전까지 비활성. 상세는 4-1절(이전 판의 '검토 요청 → 배정 → 승인/수정' 흐름을 대체) |

- **온톨로지와 라벨링 지침은 구분한다.** 온톨로지는 개념이 무엇이고 어떻게 연결되는지, 라벨링 지침은 답변을 어떤 기준으로 평가하는지 정한다.
- **정보의 출처와 확인 상태를 구분한다.** '보호자가 말함', 'AI가 추정함', '수의사가 검토함', '검사로 확인됨'은 동시에 성립할 수 있으므로 하나의 값이 아니라 출처·검토 상태·확인 근거로 나눠 기록한다. 수의사가 AI 답변을 적절하다고 평가해도 질문 속 질병이 확진된 것은 아니다.
- **'답변이 적절한가'와 '공용 지식으로 재사용할 수 있는가'는 따로 판단·저장한다.**
- 라벨 작성자(vet/operator/ai), 검토 상태(초안 → 수의사 검토 완료 → 독립 재검증 완료 / 이견), 발행 상태(미승인 → 발행 승인 → 활성화)를 각각 기록한다. 수의사 1명의 라벨은 '수의사 검토 완료', 다른 수의사의 독립 재검토까지 끝나야 '독립 재검증 완료'다.
- 수의사 검토를 받지 않은 답변·지식을 검토 완료로 표시하지 않는다. 지식은 자동 반영하지 않고 승인 → 새 버전 → 검색 영향 점검 → 활성화 순서를 거친다. 검색 영향 점검은 기존 검색 결과가 얼마나 바뀌는지 보는 참고 지표이며 품질·안전 합격 판정이 아니다. 실제 지식 발행 전에는 후보 관련 질문에서 근거와 답변이 적절한지 보는 답변 단위 확인을 추가한다(B단계, 수의사 참여 후).

### 수의사 참여 단계 (2026-11-13 현재 참여 수의사 0명)

| 단계 | 조건 | 할 일 | 완료 결과 |
|---|---|---|---|
| A | 지금 | 온톨로지·라벨링 지침 초안, HITL 검토 화면(운영자만 접근, 2026-11-14 운영 배포 `hitl-review.pawcheck.ai`), 자동 점검, 권한·이력, AI 라벨 초안, 모의 데이터로 전체 흐름 시험, 수의사 섭외 자료 | 수의사가 오면 바로 쓸 수 있는 도구 |
| B | 수의사 1명 | 초안 검토·확정, 실제 라벨링, 수정 답변·지식 후보 작성, 실제 작업 시간 측정 | 수의사가 평가한 데이터 |
| C | 수의사 2명 이상 | 같은 사례를 독립 라벨링해 기준 맞추기, 재검토, 이견 조정, 승인 → 평가 → 활성화 | 독립 재검증을 거쳐 서비스에 반영한 지식 |

- **MVP1-A(모의 흐름 PoC) 완료 기준 — 2026-11-13 달성:** 모의 데이터로 검토부터 시험 환경 활성화까지 통과하고, 미승인·모의 데이터가 운영 검색에 들어가지 못하게 차단되는 것. HITL의 효과는 수의사 참여 후 판정한다.
- AI 라벨 초안은 'ai' 작성자로만 기록하고 검토 완료로 세지 않는다. AI 제안에 끌려가는지 보려고 일부 사례는 제안을 숨기며, 숨김 여부를 기록한다.
- 수의사 섭외는 A단계와 함께 진행한다. 건당 소요 시간은 A단계에서 '운영자 시연 시간'으로만 표시한다. 수의사 섭외 자료는 MVP 완료 조건에 넣지 않는다(2026-11-14).

### 수의사 없이 진행하는 MVP1 — 출처 근거 갈래 (2026-11-14 확정)

수의사 확보 시점을 알 수 없으므로 수의사 확보는 MVP의 선행 조건이 아니다. 같은 HITL 구조를 유지하고 두 갈래로 나눈다.

| | 출처 근거 갈래 (지금) | 수의사 검증 갈래 (수의사 확보 후) |
|---|---|---|
| 기준 | 이미 있는 자료: AI Hub 수의사 답변·교재 등 원천 출처 | 새로 참여한 수의사의 판단 |
| 작업자 | AI 자동 점검 + 운영자 확인 | 수의사 2명 독립 라벨 + 승인 (B·C단계 규칙 그대로) |
| 표시 | '자동 점검 결과', '출처 대조·발행 규칙 점검 통과' | '수의사 검토 완료', '독립 재검증 완료' |
| 운영 발행 | 원문 의미·적용 조건을 보존한 정리·발췌·구조화만(아래 구현 상태 참고) | 수의사 승인 지식 |

- **자동 점검은 점검이지 검증이 아니다.** AI 대조도 틀릴 수 있고 실행마다 결과가 달라진다(2026-11-14 실제 5건에서 확인). 운영자 확인의 보조로만 쓰며 '안전성 검증', '수의학적으로 검증됨'으로 부르지 않는다. 원천 답변과의 일치는 참고 비교이며 높을수록 좋은 합격 기준이 아니다.
- **운영 발행 가능(방침)**: 원문 의미를 유지한 정리, 출처에 명시된 조건을 붙인 사례, 검색용 제목·태그·분할 개선, 원천의 누락·중복·잘못된 분할·메타데이터 수정 후 재색인.
- **구현 상태 (2026-11-14)**
  - 현재 구현: 지식 후보 발행은 수의사 갈래 규칙만 있다(운영 환경에서 운영자는 발행 승인 불가).
  - 이번 작업: 기존 원천(AI Hub)의 **본문** 정제·재색인을 기존 적재 도구(`load_knowledge`)로 한다. 제목·진료과·질병명·생애주기·메타데이터는 바꾸지 않는다(되돌리기가 본문 버전만 복구하므로).
  - 후속 작업: 출처 근거 후보의 운영자 승인 경로(basis 등), 제목·태그·메타데이터 변경과 그 복구.
  - 운영 배포(2026-11-14 완료): HITL 검토 도구(검토 화면·API·자동 점검 표시·비교 실행·되돌리기 도구)를 `hitl-review.pawcheck.ai`로 배포했다. 도구 배포이며 정제 효과나 MVP 완료를 뜻하지 않는다. 운영 DB의 검토 항목은 0건이고, 운영에 M02 검토 항목을 넣는 경로는 아직 없다(필요 시 추가).
- **발행 보류**: 특정 사례를 모든 반려견에게 일반화, 여러 자료를 합쳐 새로운 의학적 결론 생성, 출처 간 충돌을 운영자나 AI가 임의로 해결, AI가 새로 만든 의학적 설명.
- **운영자 확인 범위**: 운영 발행 후보는 전부 확인한다. 일반 점검 결과는 문제 사례와 '문제 없음' 판정 일부를 표본으로 확인한다(AI가 놓친 오류가 빠지지 않게).
- **수의사 갈래의 엄격한 규칙은 유지**하되 지금 개발을 막지 않는다. 이견 조정 기능·수의사 승인 조건 추가 개발은 멈춘다.
- **현재 MVP 완료 기준(출처 근거 개선·반영·복귀 가능)**: 실제 질문에서 발견한 문제를 출처에 근거해 수정하고, 답변 비교와 운영자 승인을 거쳐 검색에 반영하며, 되돌릴 수 있는 것. 모의 흐름 PoC(MVP1-A) 완료만으로 MVP가 끝나지 않는다.

#### 진행 방법 — 작은 변경을 비교하고 되돌릴 수 있게 (2026-11-14 확정)

실제 5건 점검에서 두 가지를 발견했다. ① 답변이 근거에 없는 조언을 한 문장씩 덧붙인다(5건 중 4건, 자동 점검 지적 — 원문 대조로 확정 필요). ② 원천 질문·답변에 질문 의미와 무관해 보이는 반복 문구가 있다(문구 탐지 비율 질문 약 19%, 답변 약 16%. 오류율·삭제 대상 비율이 아니며, 발생 원인은 확인하지 않았다). 운영 Neon 재색인부터 하지 않고 다음 순서로 진행한다.

| 순서 | 작업 | 완료 기준 |
|---|---|---|
| 1 | 기존 도구 확장: 실행 기록, 프롬프트 선택, 되돌리기 | 테스트 통과, 로컬에서 새 버전 활성화 → 이전 버전 복귀 확인 |
| 2 | 반복 문구 대표 표본 10~15건 + 애매한 문구 제시(삭제 전후·제거 이유) | 사용자가 '제거할 문구'만 확정. 애매한 것은 유지 |
| 3 | 같은 15건(개발용 5 + 확인용 10)으로 현재/수정 프롬프트 비교 | 근거 없는 추가 조언과 답변 누락을 실제 답변으로 확인 |
| 4 | 정제가 필요한 문서만 로컬 새 버전으로 적재해 비교(수정 프롬프트 고정) | 무관한 답변 감소, 새 중복 확인 |
| 5 | 결과가 엇갈리는 사례만 추가 실행 | 변화가 반복되는지 확인 |
| 6 | 운영 반영 준비 | 변경 목록, 실제 비용, 되돌리기 방법 제시 → 사용자 승인 후 반영 |

**진행 결과 (2026-11-14)**
- 1단계(실행 기록·프롬프트 선택·되돌리기)와 2단계(정제 후보 검토 자료) 완료. 3단계 완료: 같은 15건에서 수정 프롬프트 `strict-sources`(근거 없는 개별 조언 금지)는 **채택하지 않음**. 근거 없는 주장은 줄었지만 근거에 있던 필요한 내용이 빠지고 목록이 미완성으로 끝나는 결함이 생겼다. 현재 프롬프트를 유지한다.
- 원인 파악: ① 점검기가 근거 앞 600자만 보아 '근거 없음'을 잘못 판정(점검기 v.4로 수정, 저장된 답변 재채점). ② 답변이 원천의 반복 문구(처방 용량·세척 방법 등)를 그대로 가져와 불필요한 조언이 생김. 정제 효과는 아직 측정하지 않았다.
- 현재 프롬프트의 남은 문제: 응급·내원 기준을 근거 없이 넓히는 등 '안전 쪽으로 덧붙인 문장'도 근거가 있다는 뜻은 아니다. 기록만 하고 추가 실험은 하지 않는다.
- 4단계(정제 데이터 비교)는 보류. 15건 비교에서 검색된 문서 중 정제 후보가 있는 58건은 **삭제 승인 목록이 아니라 검토 후보**로 보관한다(`data_output/eval/cases/trial_clean_ids.json`, 규칙 clean-draft-2026-11-14.5). 전체 정제는 승인되지 않았다.

- 15건은 전체 성능 향상의 입증이 아니라 '발견한 오류가 줄고 뚜렷한 부작용이 없는지' 확인하는 규모다. 결과도 그 범위로만 보고한다.
- 만들지 않는 것: 별도 평가 시스템·대시보드, 부분 되돌리기, 새 평가 체계. 출처 근거 발행 구조(basis 등)와 설계 문서 전체 개편은 이 비교 뒤로 미룬다.

## 4-1. M03 — 보호자·수의사 질문·답변 연결 (2026-11-14 기획 초안, 사용자·Codex 검토 대기)

수의사가 아직 없어도 **시험 계정으로 전체 흐름을 개발·검증**한다. 실제 수의사 확보와 운영 조건(비대면 상담 법률 검토 등)은 **실서비스 개방 조건**이며 기획·개발·시험을 막지 않는다.

### 세 주소의 연쇄

| 단계 | 주소 | 사용자 | 하는 일 | 다음 단계로 넘기는 것 |
|---|---|---|---|---|
| ① 상담 | twinvet.pawcheck.ai | 보호자 | AI 상담, 수의사 선택·연결 요청, 고른 질문 공유, 회신 확인 | 보호자가 고른 질문 1건의 공유 사본(질문·AI 답변·동의한 반려견 정보) |
| ② 회신 | vet.pawcheck.ai | 수의사 | 연결 요청 수락·거절, 받은 질문 열람, 회신 | 회신 → 그 보호자에게만 표시 |
| ③ 품질 검토 | hitl-review.pawcheck.ai | 검토 수의사·운영자(관리자) | AI 답변 평가·지식 후보(M02), 운영자: 운영자 현황 | 공용 지식 개선(기존 승인·검색 영향 점검·활성화 규칙) |

- **현재 HITL에 보호자에게서 오는 정보 (2026-11-14 코드 확인)**: 없다. 답변 피드백(도움 됨/안 됨·의견 300자)은 저장되지만 상담과 함께 만료 후 삭제되고 HITL로 가지 않는다. 검토 묶음의 출처 `consultation`은 스키마에 허용만 돼 있고 만드는 경로가 없으며, 데이터모델 4절에서 동의·비식별화·보관 기간 확정 전에는 만들지 않기로 했다.
- **②→③ 연결 규칙 (M03에서 새로 둠, 2026-11-14 Codex 검토 반영)**: 자동 편입하지 않는다. 보호자가 질문을 보낼 때 **별도 선택 동의('서비스 품질 개선에 활용', 기본 꺼짐)**를 한 질문만, 수의사 회신이 끝난 뒤, 운영자가 hitl-review의 **이관 화면에서 질문·AI 답변·덧붙인 설명·수의사 회신 본문까지 읽고 이름·연락처·주소 등 식별 정보를 지운 '운영자 정리 사본'**을 만들어 HITL 검토 묶음(origin=consultation)으로 넘긴다. 반려견 이름·건강 메모는 처음부터 넣지 않는다. 정리했다고 비식별이 보장되지는 않으므로 '비식별'로 부르지 않는다. 사본은 원본 공유 질문과 연결을 유지하고, **보호자가 질문을 삭제하거나 동의를 철회하면 그 검토 사본과 라벨도 함께 삭제**한다(그 사본에서 나온 지식 후보·발행 지식 처리는 아래 이관 조건 ③). 수의사 회신은 **참고 답변**이며 라벨이 아니고 검토 완료로 세지 않는다. 이후는 M02 규칙 그대로다. AI 답변과 수의사 회신이 다른 사례는 검토 우선순위를 높인다.
- **HITL 이관 조건 (2026-11-14 Codex 검토, 이관 구현 전 필수)**: ① **철회와 이관의 경합**: 이관 저장 직전에 같은 트랜잭션에서 질문 행을 잠그고 동의·삭제·회신 상태를 다시 확인한다. 철회·삭제는 같은 행 잠금을 거친다. 그래서 '철회 후 이관'은 거부되고 '이관 후 철회'는 사본을 지운다. 어느 순서든 사본이 남지 않는다. ② **이관 후 회신 정정**: 이관할 때 사용한 회신 버전(vet_reply_revision id)을 검토 묶음에 기록한다. 이후 정정되면 그 묶음을 '재확인 필요'로 표시하고 기존 라벨을 덮어쓰지 않는다. 새 버전 반영은 운영자가 다시 정리해 별도로 이관한다. ③ **삭제된 사본에서 나온 지식 후보**: 후보는 승인 해제·발행 차단. 이미 발행된 지식은 검색에서 제외(비활성화)한 뒤 남은 근거로 다시 검토한다. 자동 재발행 없음.
- **운영자 현황·분석 (hitl-review, 운영자 전용)**: 운영자는 관리자 계정이므로 M03 운영 상태를 볼 수 있어야 한다. 다만 **일반 DB 조회·대시보드는 만들지 않고** 두 가지만 둔다. ① **M03 현황**(숫자만, 본문 없음): 연결 요청·수락·거절·해제 수, 질문 대기·회신·취소 수, 회신까지 걸린 시간(중앙값·최대), 품질 개선 동의율, 이관 대기·완료 수, 기간 선택. ② **이관 대기**: 동의 + 회신 완료 질문만 본문을 보여 주고 정리 → 이관한다. **동의하지 않은 질문의 본문은 운영자에게도 보이지 않는다.** 같은 숫자는 명령(`hitl_admin m03-stats`, 읽기 전용)으로도 보며, 화면과 명령은 같은 집계 함수를 쓴다. 더 깊은 분석은 운영 DB 읽기 전용 조회로 하고, 상담 본문은 대상이 아니다.
- 수의사 회신은 공용 RAG 지식으로 자동 발행하지 않는다(③의 승인 경로만).

### 이번에 만들 흐름

| 순서 | 기능 | 기준 |
|---|---|---|
| ① 수의사 선택 | 운영자가 등록한 수의사 목록에서 골라 연결 요청 | 주치동물병원 검색·등록(P08)과 별개 |
| ② 연결 승인 | 수의사가 수락·거절 | 승인 전에는 상담 내용을 공유하지 않음. 승인은 질문마다 반복하지 않음 |
| ③ 질문 공유 | 보호자가 보낼 질문(AI 답변 1건 단위)을 고르고, 필요하면 '수의사에게 덧붙일 설명'을 적고, 공유 내용을 확인한 뒤 전송 | 그 질문·AI 답변·덧붙인 설명·동의한 반려견 정보만. 전체 대화는 보내지 않음. 연결돼도 다른 상담은 자동 공유하지 않음 |
| ④ 수의사 회신 | 받은 질문 확인·답변 작성·전송 | 본인에게 온 질문만 열람 |
| ⑤ 보호자 확인 | 원래 질문에서 대기·답변 완료 상태와 회신 확인 | AI 답변과 수의사 답변을 명확히 구분 |

- 최소 운영 규칙: 보호자는 본인의 요청·답변만, 수의사는 자신에게 온 요청만 본다. 회신 전 요청 취소, 연결 해제를 지원하고 해제 후에는 새 질문을 보낼 수 없다. 공유 시점의 내용을 저장해 이후 프로필·대화가 바뀌어도 전달 내용은 그대로다. 보호자는 앱에서 회신을 확인하고, 재접속용 확인 링크는 추측할 수 없는 토큰으로 만료·폐기 기준을 둔다(데이터모델 4-1절).
- **이번 범위에서 제외**: 병원 조직·직원 관리, 카카오·이메일 알림, 결제, 예약, 실시간 채팅, 수의사 답변의 자동 지식 발행, ②→③ 자동 편입.
- **구현 순서 (2026-11-14 Codex 승인)**: 연결 → 질문 → 회신 → 보호자 확인을 먼저 구현·보고(권한 테스트 증거 포함). 운영자 현황은 함께 진행 가능. HITL 이관은 그다음에 위 이관 조건과 함께 붙인다. **현황(2026-11-14)**: 연결·질문·회신·보호자 확인 구현과 권한 테스트 완료(개발명세 7-1절 구현 현황). 운영자 현황·HITL 이관(이관 조건 ①②③ 포함)도 구현(개발명세 7-1절). 운영 배포 전 · M03 꺼짐.
- **진행 순서**: 기획(이 절과 사용자흐름 5절·데이터모델 4-1절·개발명세 7-1절·화면설계 6절 M03) → 개발(연결 요청 → 질문 전달 → 회신 → 보호자 확인 → 운영자 현황·이관 화면) → 시험 보호자·수의사 계정으로 검증 → 배포(실서비스 개방 전까지 화면·API 모두 비활성).
- **개발 완료 기준**: 시험 보호자가 수의사를 선택하고, 수의사가 승인한 뒤, 보호자가 고른 질문만 전달되고, 수의사의 답변을 해당 보호자가 확인하며, 다른 계정은 접근하지 못한다. **연쇄 기준**: 품질 개선 활용에 동의하고 회신이 끝난 질문만 운영자 정리를 거쳐 HITL 묶음으로 만들 수 있고, 미동의·취소·삭제된 질문은 거부되며, 삭제·동의 철회 시 만든 묶음도 지워진다.

### 데이터 활용 결정 — 혼합안 (2026-11-13 확정)

- 현재 AI Hub 데이터 전체(Validation 포함)를 지식 구축과 라벨링 대상으로 활용한다. 이는 지식 확보를 우선하는 **제품 결정**이다. 이용 조건 확인은 59번 전체에 걸린 기존 선행 확인 항목으로 유지한다(Training·Validation은 분할 이름일 뿐 이용 조건은 같다).

- 원천 ID·중복 그룹·분할표·사용 이력을 기록한다. 분할표는 고정 seed로 지금 만들어 두고, 이후 모델 재개발 때 학습/평가에 쓴다. 같은 상담·중복 사례는 같은 분할에 둔다.

59번은 반려견 자료이므로 다른 동물까지 답변 범위를 자동 확장하지 않는다. 153번(반려동물 안구질환)은 사용하지 않는다(사용자 결정, PoC·MVP 모두 제외). 59번의 이용 조건·재배포 범위·품질은 별도 확인이 필요하다. 필드 매핑은 데이터모델 설계서, 개발환경과 경로 설정은 개발명세서를 따른다.

## 8. 이번 확정 사항

- 동물 선택 UI·종 필드를 두지 않고 반려견만 지원한다.
- 생애주기 선택 UI는 두지 않는다. 대신 보호자가 **이름(선택)**, **품종·나이(필수)**와 **건강상태(선택: 체중, 중성화 여부, 기존 질환·복용 약)**를 입력하고, 서비스가 이를 답변 판단에 사용한다.

  - 품종별·건강상태별 주의사항은 검색 근거가 있을 때만 언급한다. 근거 없는 품종 일반화를 하지 않는다.
- 고양이 등 반려견 외 동물 질문은 지원 범위 밖으로 안내한다. 59번 질의응답 21,606건 중 고양이 상담은 1건뿐임을 전수 확인했다.

- 원천 교재·학술지의 검색·생성 활용 및 원문 노출 조건을 공개 배포 전에 확인한다. 짧은 발췌도 허용된 것으로 가정하지 않으며 확인 전 문서명·출처만 표시한다.
